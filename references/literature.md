# Literature: the shared pool (phase 1), the tool hunt (phase 4), on-demand lookups, the final re-sweep

The pool is one growing, shared knowledge base for the whole campaign, not a one-off survey.
- Every agent reads it before searching.
- Every agent writes what it finds back to it.
- Close-reading notes in it replace re-reading the same paper; several agents reading the same papers was a large
  hidden cost last time.

Files:
- `lit_pool/<label>.md`: one shard per agent;
- `lit_pool.md`: the merged index, generated by `merge_pool.py`;
- `lit_pool/README.md`: the entry format.

## Why it is built this way

- **The search covers far more than arXiv.** A record-level result we once spent a sub-campaign re-deriving had been
  posted only on the author's faculty page. A hit that pointed to that page was never opened. So the sweep:
  - searches the explicit target strings (numbers, tuples, record values), not just topic words;
  - covers personal and faculty pages, trackers, GitHub and X;
  - requires every plausible hit to be opened.
- **Title and abstract search misses results that live only in a paper's body.** A methods paper (machine
  learning, optimisation, computer-assisted proof) may report a record on our problem without naming it in the
  abstract or filing it under our field. The available web search summarises pages rather than indexing full
  text, so the sweep and V1 run a methods-paper sweep: collect recent AI/computational-discovery papers in
  general, open each one's full text, and search the body for our problem (see prompts/lit_sweep.md).
- **Released artifacts are part of the literature.** The construction, certificate or code behind a record is
  often the best starting point for an attack: one run that started from a released record construction beat
  that record, while a run that knew the record but started from scratch ended below a ten-year-old value. Every
  target entry records `artifacts:`.
- **Rough first, verify second.** Rough-then-verify is cheaper than one careful pass. Breadth is cheap, while
  checking each claim against its source costs real effort. Splitting the two lets the verifiers specialise by
  source class, and also go looking for what the rough pass missed.
- **Verification is about citation accuracy, not refereeing.** It asks: does the source really say this, with this
  number, date and attribution? Others' mathematics is used as given (the user's standing rule).

## Phase 1, step by step

1. **L0, the rough sweep.** One agent, `make_prompt.py --kind lit_sweep --label L0`.
   - If the kickoff inherited an older pool, tell L0 in `--extra` to sweep only what is newer than the inherited
     date, plus anything the old pool lacks.
   - When it returns, run `merge_pool.py`.
2. **V1..Vk, verify and fill gaps.** Run these in parallel, as many as the budget allows (typically 3-4). Split the
   rough entries by SOURCE CLASS so the gap searches do not overlap:

   | agent | source class |
   |---|---|
   | V1 | arXiv + journals by title/abstract, plus the methods-paper sweep (full texts of recent AI/computational-discovery papers) |
   | V2 | personal and faculty pages of every author in the target entries, plus their students and coauthors |
   | V3 | trackers, wikis, GitHub, X/Mathstodon, blogs, lab releases |
   | V4 | cross-field: the same structure under other names (optional if the budget is tight) |

   Put each agent's slice and source class in `--extra`. Then run `merge_pool.py`.
3. **R1..Rm, close reading.** Read the verified target and tool entries that matter, split by TOPIC so that each
   reader sees a coherent body of work.
   - `merge_pool.py` prints "verified + relevant but not yet read".
   - Give each reader 3-6 sources in `--extra`.
   - Two launches on the same sources are duplicates only if they would hand back the same deliverable. A reader
     returning notes and an agent returning a calibrated computation from the same papers are NOT duplicates; do
     not merge them. If they share some reading, trim the shared part from the later one and point it at the
     earlier one's notes.
   - Always close-read the record-setting paper itself: phase 2 needs its parameters.
   - Readers write notes back as same-ID update cards: exact theorems with hypotheses, constants, how the record is
     assembled, obstructions with their location, and reusable code.
   - Run `merge_pool.py`.
4. **Coordinator after the merge:**
   - Anything plan-changing (scoop, record moved, the same target already claimed) goes to the user before
     phase 2.
   - Every entry listed under "entries naming obstructions" gets a barrier card in `barriers.md`, with the pool ID
     as evidence. This is how stated obstructions stop being rediscovered by attack agents.
   - Set META `stage: 1-literature` done in the stage log.

Do not re-check entries a verifier already marked verified: that is the one check.

## Phase 4, the tool hunt

Run it after the tree exists (phase 3), because a precise node statement makes a precise query. Generic "tools
for problem X" searches mostly produced leads that failed last time.

**Mode A, per bottleneck node.** Do this once per campaign.
- Run one agent per bottleneck node: the AND-child with the largest gap first. Use
  `make_prompt.py --kind tool --label TH-N2 --node N2 --extra "Mode A: tools for this node"`.
- Each agent searches all source groups (same field, cross-field, AI-math outputs), in several vocabularies.
- Candidates come back as pool entries (relevance: tool, nodes: N2), each with hypotheses checked against our
  setting.
- The coordinator turns the good ones into route cards (phase 6). They still go through the ceiling gate.

**Mode B, barrier-triggered.** This runs throughout the campaign.
- Every new barrier card triggers one tool agent:
  `--extra "Mode B: has anyone got around barrier B03? how?"`, with `--node` set to the node the barrier blocks.
- Set the barrier's `workaround_search: pending`, then `done -> <pool IDs>`.
- A barrier is the next thing to attack, not a verdict.

## On-demand lookups (pool phase 4)

Every agent prompt already says: check the pool first, search only if it is missing, write finds back with
`trigger:`. The coordinator follows the same rule: before answering a literature question from memory, grep
`lit_pool.md`. After agents return, run `merge_pool.py` if any shard changed.

## Final re-sweep (phase 12)

Before any record claim, `audit_lit` searches again for the exact claimed numbers, and for every record value
between the old record and ours. Give the date of the last sweep in `--extra`. A scoop found here goes to the
user immediately.
